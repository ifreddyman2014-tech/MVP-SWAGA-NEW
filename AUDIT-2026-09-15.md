### 1.4 MRR — два метода

| Метод | Расчёт | Результат |

## 2. Причины багов

### 2.1 Duplicate email на FR, US1, US1-xHTTP, UK-xHTTP

**Файл:** `bot.py`  
**Механизм:**

```
Продление подписки → handle_payment_success() (bot.py:2857)
 ├─ update_client() на основном сервере (bot.py:2891) → OK (expiry обновляется)
 └─ _sync_client_to_other_servers() (bot.py:2904)
      └─ для каждого сервера кроме primary:
           └─ _server_add_client() (bot.py:1898)
                └─ srv_xui.add_client() (xui_api.py:94)
                     POST /panel/api/inbounds/addClient
                     ← ответ: {"success": false, "msg": "Duplicate email: tg_XXX_YYY"}
```

**Ключевые строки:**

- `_sync_client_to_other_servers`, bot.py:1924–1939: всегда вызывает `_server_add_client`, никогда `update_client`
- `_server_add_client`, bot.py:1874–1901: для non-WS серверов → `srv_xui.add_client()`
- `add_client`, xui_api.py:94: POST addClient — создание, не обновление
- Нет ни одного `getClientByEmail` / поиска перед `addClient`

**Почему именно FR, US1, US1-xHTTP, UK-xHTTP:**

| Сервер | transport | путь при sync | результат |
|---|---|---|---|
| fr1 | tcp | `_server_add_client` → xui add_client | **Duplicate email** |
| us1 | tcp | `_server_add_client` → xui add_client | **Duplicate email** |
| us1-xhttp | xhttp | `_server_add_client` → xui add_client | **Duplicate email** |
| uk1-xhttp | xhttp | `_server_add_client` → xui add_client | **Duplicate email** |
| fr1-ws | ws | `ws_manager.add_client()` перезаписывает JSON | нет ошибки |
| us1-ws | ws | `ws_manager.add_client()` перезаписывает JSON | нет ошибки |
| uk1 | ws | `ws_manager.add_client()` перезаписывает JSON | нет ошибки |
| us2-ws | ws | `ws_manager.add_client()` перезаписывает JSON | нет ошибки |
| us2 | tcp | **primary** → update_client | нет ошибки |

Основной сервер большинства активных пользователей — us2 (high priority). `_sync_client_to_other_servers` пропускает primary. Остальные xui-серверы получают повторный `addClient`. WS серверы избегают ошибки потому что ws_manager перезаписывает весь JSON-конфиг.

**Последствие:** при каждом продлении expiry на FR, US1, US1-xHTTP, UK-xHTTP НЕ обновляется. Клиент со временем перестаёт подключаться к этим серверам, хотя в БД подписка активна. Логи 13.09.2026 подтверждают:
```
[ERROR] sync: FAILED to add/update tg_5110354152_1789291877 on США 1 xHTTP
[ERROR] sync: FAILED to add/update tg_5110354152_1789291877 on Великобритания xHTTP
```

**Также:** `_create_subscription_on_server` (bot.py:2050–2051) — проверка `existing_sub` происходит ПОСЛЕ отправки ссылки на оплату (строка 2048: `return`). Ветка trial/платная пересекается с этим же `existing_sub` на строке 2051, что ведёт к тому, что `plan` в БД не обновляется при продлении (см. п. 1.3).

### 2.2 Plan остаётся 'trial' при продлении

**Файл:** `database.py`, `bot.py`  
**Строки:** bot.py:2864 (`extend_subscription_to_date`) — нет аргумента `plan`

Функция `extend_subscription_to_date` обновляет только `end_date`:
```python
# database.py — функция обновляет только end_date, не plan
UPDATE subscriptions SET end_date = ?, is_active = 1 WHERE user_id = ? AND is_active = 1
```
(точный номер строки в database.py: функция `extend_subscription_to_date` около строки 167–191, проверить grep)

`handle_payment_success` при продлении (ветка `existing_sub`, bot.py:2864) не вызывает отдельного UPDATE для поля `plan`. Если у пользователя была trial-подписка (plan='trial'), и он заплатил за 1m, поле `plan` остаётся 'trial'.

### 2.3 UK-xHTTP JSON decode error — отдельная от Duplicate email проблема

**Файл:** `xui_api.py`, `servers.py`  
**Механизм:**

Сервер uk1 / uk1-xhttp: `xui_ssl: false` → URL строится как `http://163.5.210.147:3226/HMy1GrTZpItXDZ8pv4`.

Прямой запрос `GET http://163.5.210.147:3226/HMy1GrTZpItXDZ8pv4/` возвращает **HTML логин-страницу 3X-UI** (полная страница ~3KB, статус 200). Панель жива и отвечает.

`health_check` (servers.py:209–259) делает:
1. GET `/` → получает HTML → парсит CSRF-токен ✅
2. POST `/login` с `data={"username":..., "password":...}` → должен вернуть `{"success": true}`

Если POST `/login` возвращает HTML вместо JSON (например, неверные учётные данные → редирект на login, или версия 3X-UI изменила формат ответа) → `resp.json()` / `json.loads(raw)` бросает исключение → `health_check` ставит `is_healthy=False`.

Логи 14.09.2026 23:00:
```
[WARNING] servers: Health check failed for Великобритания:
[WARNING] servers: Health check failed for Великобритания xHTTP:
```
(сообщение обрезано — конкретный текст исключения не дошёл до лога)

**Почему именно UK, не другие:** только uk1 и uk1-xhttp имеют `xui_ssl: false` + `xui_host: 163.5.210.147`. По changelog 11.07.2026: «3X-UI панель на 163.5.210.147:3226 возвращает 404 на все пути» — это была известная нерешённая задача. По состоянию на 15.09.2026 панель отвечает (HTML 200), но авторизация не проходит. Что именно возвращает `/login` endpoint — не проверено в read-only режиме (требуется SSH + curl).

Также: у uk1-xhttp `inbound_id: 2`, а у uk1 тоже `inbound_id: 2` — оба сервера смотрят в один inbound. При попытке добавить клиента через uk1-xhttp используются те же учётные данные uk1, что усугубляет проблему.
